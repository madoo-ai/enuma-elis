Python code mode Compared with native tools
01 — Pitch

Python code mode vs native tools

What we expect to change, what the latest rerun already shows, and what we still need to measure.

02 — The claim

Native tools spend a model turn on every small step.

Code mode lets the model put several reads, one wait, and one check into a single program. The program then returns only the result the model needs.

That should mean fewer turns, fewer child calls, and less context.

04 — What we expect against native tools

The same work should cost fewer turns and less context.

Fewer model turnsOne program can replace several tool calls.
Fewer child callsReads and waits can batch instead of repeating.
Less uncached inputA program can return an excerpt, not a whole file.
Fewer repeated readsState can stay inside one program when it belongs together.
Shorter failure pathsOne program reports the line and the result together.
Clearer evidenceThe model can compute a check and return the value it proved.
05 — What still needs to happen

One deployment step is still missing.

The latest dump still shows wait_url(timeout=...) and bare-function evaluate() failing, which means the browser SDK in the runtime has not been refreshed. The fork-side output fixes are active, but the browser fixes are not yet fully in play.

Issue #10 also remains open: generated build output can still reach the QA prompt.

06 — The ask

Refresh the runtime, then run one controlled comparison.

Give us one run against native tools on the same goal and the same model. If code mode still wins on turns, tokens, and time, we keep going. If it doesn’t, we stop and say so.

Latest rerun: 226 programs, 1,011 child calls, 36.5 active minutes, 479k uncached input tokens. Previous run: 572 programs, 2,101 child calls, 71.2 active minutes, 3.6M uncached input tokens. The two runs used different templates, so treat the comparison as directional.
