Python code mode An experiment in fewer turns and fewer tokens
01 — What we’re doing

Python code mode: fewer turns, fewer tokens

This repo is an experiment in replacing a burst of native tool calls with one Python program. The model writes a program, the program does the routine work, and the model gets one result back.

That should cut model turns, cut context, and save time. The latest run already shows the direction.

02 — Why it should help

Native tools make the model ask for every piece separately.

One program can read several files, wait once, compute a check, and return only the value the model needs. Native tools would turn those same steps into separate model turns.

Fewer turns mean less context, fewer round trips, and less waiting.

03 — Why Python

Python is the shortest path from intent to result.

No new DSLThe model already knows Python.
ReadablePrograms are easy to inspect and debug.
ComposableLoops, conditions, and state fit naturally.
Familiar failuresOne stack trace says what broke.
04 — Why code mode

One program replaces a burst of tool calls.

Fewer turnsSeveral tool calls become one model turn.
Less contextThe program returns one short result.
Less waitingIt can wait once instead of polling repeatedly.
Clearer evidenceOne trace reports the whole check.
05 — The tool surface we target

The same tools the model already uses, wrapped in Python.

Module What it covers Why it matters
fs Read files, list paths, search text. Most routine turns start here.
shell Run commands, tests, and builds. This is where latency and tokens pile up.
browser Inspect pages, click, fill, and wait. UI checks are the slowest part of the loop.
mutate Apply edits and patches. Keeps changes typed and auditable.

We are not targeting arbitrary Python execution. We target the existing tool surface the agent already uses.

06 — What changes in practice

Four examples show the difference.

Task Native tools Python code mode
Read three files Three separate calls, three separate turns. One program reads all three and returns one summary.
Wait for a dialog The model polls the page again and again. One wait runs until the page is ready.
Check a test result The model reads the full output and decides. The program parses the result and returns pass or fail.
Recover from an error The model sees one error and starts over. The program catches the error and returns one trace.

These snippets are illustrative, not verbatim API calls.

Native tools

Python code mode 
from agent import fs

paths = ["src/a.py", "src/b.py", "src/c.py"]
out = {p: fs.read(p, limit=80).text for p in paths}
return out

07 — What the latest run shows

The latest run already moved in that direction.

About 4.5× fewer model turns 226 programs did the work of 1,011 native tool calls. An equivalent native-tools run would need roughly 4.5× more model turns.
Several times less token cost Each extra turn carries context again. Code mode returned short results instead of full tool output, which kept uncached input at 479k tokens. An equivalent native-tools run would carry more context and more tokens.
08 — How the numbers back it up

The run is small, but the direction is clear.

One program replaced about four native tool calls on average. Active time stayed under 37 minutes. Uncached input stayed under 500k tokens. Only seven outputs were truncated, and the old 25-second browser stall did not appear.

An equivalent native-tools run would incur more turns and more tokens for the same work.

09 — What we’re not claiming yet

This is an experiment, not a benchmark.

We have one clean run, not a controlled native-tools comparison. The numbers show what a fixed code-mode run costs today. They do not yet give the exact multiplier for tokens against native tools.
