Python code mode Latency and token cost, measured on one real goal
01 — Title

Python code mode: cut latency, cut tokens

One real goal ran for 71.9 minutes and produced 572 Python programs. The work finished. The bill was too high.

Four browser calls and one QA prompt caused most of the extra time and cost. We fixed the browser calls. The QA prompt is now issue #10.

02 — What the run looked like

The mode already works. The cost around it does not.

Python code mode completed 94.2% of its programs on the first attempt. The goal still needed four QA rounds, but the programs themselves ran. What stood out wasn’t correctness. It was where the minutes and tokens went.

03 — Where the time went

One browser call took 629 seconds and still reported success.

The model waited 45.9 minutes. Tools took 25.3 minutes. Inside that tool time, one browser call, wait_load, cost 629 seconds across 25 calls. Every one of those calls looked successful to the harness.

Model time
45.9 min
Tool time
25.3 min
wait_load alone
629 s
The fix was small: wait_load now checks document.readyState and returns when the document is ready. No 25-second stall, no false success.
04 — What broke

Four browser calls caused most of the visible waste.

These weren’t exotic failures. They were ordinary browser calls that either stalled, matched nothing, or silently did nothing.

  • wait_load stalled 25 seconds per call.
  • wait_for(role="dialog") couldn’t see structural nodes.
  • wait_url timed out even when the URL already matched.
  • evaluate returned an empty object for bare functions.

Nine polling programs produced 671 browser calls. All nine failed. That’s close to one third of every child call in the run.

Six evaluate calls didn’t execute at all. The browser returned an empty object and the program still completed.

05 — Where the tokens went

Most uncached input came from one QA prompt, not from code.

Four QA requests carried 2.59 million uncached input tokens. That’s 72.1% of the entire run’s uncached input. The cause was generated build output and database files in the diff sent to QA.

One line in the QA prompt was 230,341 characters long. That line came from a minified bundle, not from source code.
06 — The hidden output problem

Print output hid its own truncation.

Ninety-three of the 572 programs had output cut short. The metadata still said truncated: false. The model kept reading the same files again to recover the missing pieces.

93 Programs with truncated print output
16% Share of all programs affected

The renderer kept the last 60 lines and never reported what was missing. We changed that. Success output now keeps the head and tail, and failure output keeps the tail. Every program reports the omitted line and character counts.

07 — What we changed

The fixes are already on main.

These are not proposals. They’re merged, tested, and built into the current binary.

Waitswait_load, wait_url, and wait_for now check the real page state instead of waiting on events that never fire.
Function callsevaluate invokes bare functions, so probes actually run.
OutputPrint output keeps head and tail and reports omitted counts.
ReadsThe catalog teaches the model to batch independent reads and return keyed excerpts.
Errorsfs.grep reports a missing path instead of searching the parent directory.
